# 补帧的运动估计与 HDR：同一个域吗？

这份表由 `scripts/report_fi_domain.py` 跑 `tools/fi_domain` 生成（`run_all.sh` 的 `0x/5` 会挡漂移）。

## 为什么这个问题值得单独一份报告

上游的补帧在 `fi_mv_setup` 里写死了两个常数，都是在 **8 位 sRGB 编码域** 上标定的：

- `match`：`if (zsad <= best * 1.02 + 0.05) bd = int2(0);` —— SAD 的绝对偏移 0.05
- `spread`：`if (all(abs(cur.read(gp).rgb - prev.read(gp).rgb) < 0.004)) v = float2(0);`
  —— 逐通道差 0.004，约等于「差不到 1 个 8 位码值」（1/255 = 0.00392）

我们把 HDR 的补帧输入换成了 `RGBA16Float`（线性、可 > 1）。`texture.read()` **不解码**，
所以 luma 提取读到的值从「sRGB 编码」变成「线性」——两者的数值尺度完全不同：
线性 0.18 == 编码 0.46；线性 0.004 == 编码 0.06（约 15 个码值）。

## 实测

同一张照片 + ±1 码值确定性噪声（代表压缩/时域抖动下最温和的帧间差异）：

```
照片                             域                        SAD中位 SAD零比 静止命中 偏零可用
build/real/p_Clouds_by_Tibor_Mokanszki.ppm 8 位 sRGB 编码域        0.02737     0.0%   100.0%    1.83×
build/real/p_Clouds_by_Tibor_Mokanszki.ppm 16F 线性域（当前实现）  0.02326     0.0%    57.5%    2.15×
build/real/p_Clouds_by_Tibor_Mokanszki.ppm 16F 转回编码域（本工具验证的修法）  0.02792     0.0%   100.0%    1.79×
                                   8 位 sRGB 编码域        0.02752     0.0%   100.0%    1.82×
                                   16F 线性域（当前实现）  0.01810     0.0%    64.4%    2.76×
                                   16F 转回编码域（本工具验证的修法）  0.02742     0.0%   100.0%    1.82×
                                   8 位 sRGB 编码域        0.02705     0.0%   100.0%    1.85×
                                   16F 线性域（当前实现）  0.02780     0.0%    44.2%    1.80×
                                   16F 转回编码域（本工具验证的修法）  0.02595     0.0%   100.0%    1.93×
```

列的含义：
- **SAD中位**：逐 8×8 块同位置的 SAD 中位数（就是 `zsad` 的量级）
- **SAD零比**：SAD 恰好为 0 的块占比
- **静止命中**：「前后两帧这个像素一样」（`<0.004`）的像素占比 —— 这张图前后内容相同，**理想是 100%**
- **偏零可用**：`0.05` 相当于多少个噪声块 SAD（>1 说明偏零偏移大于噪声底，仍能挡住乱跳）

## 结论

1. **`0.004` 这条真坏了**：8 位路径 100% 命中，16F 线性域只有 **44–64%** ——
   界面、字幕这类静止区域有一半被判成「动了」，会被运动矢量搬走（鬼影）。
2. **`0.05` 这条没坏**：两域的 SAD 中位都在 0.018–0.028，`0.05` 相当于 1.8–2.8 倍噪声底，两域都够用。
3. **修法**：16F 输入时先把线性值转回 sRGB 编码域再算 luma / 比差（`to_enc`，`enc` 由
   `cur.pixelFormat == MTLPixelFormatRGBA16Float` 决定）。静止命中回到 **100%**，
   SAD 中位回到 0.026–0.028 —— 与 8 位路径一致。

## 边界

这个工具不跑 Metal：它假设 `down` 的 4×4 平均与 `match` 的 8×8 块布局（与 MSL 同构），
但**不能**证明 Metal 编译器对 `select`/`pow` 的实现与我这里的 float 一致。
真正的保护是 `scripts/check_landing.py` 的 6 条结构断言（`to_enc` 存在、down/spread 都用它、
`enc` 由源格式决定、两处 dispatch 都绑了 buffer）——它挡的是「有人把这段改回去」。
