# 换了纹理格式之后，上游那些假设还成立吗

这份表由 `scripts/check_format_assumptions.py` 生成（`run_all.sh` 的 `0y/5` 会挡漂移）。

补丁把上屏画布从 `BGRA8Unorm` 换成 `RGBA16Float`（HDR）。换格式牵动的不是一处：补帧、
直方图、拷贝管线、重采样 view 都读这块纹理。上游写这些代码时只有 8 位，所以很多假设是
**隐含**的——pitch、字节/像素、像素值域、是否 sRGB 解码。这类假设错了不会崩、不会报错，只会画错。

| # | 假设 | 现在 | 不成立会怎样 |
| --- | --- | --- | --- |
| A1 | 运动矢量图是 RG16Float（位移 float2 不被截断） | ✓ | 改成 8 位格式会把 ±16 像素的位移量化成 1/255，运动矢量全错，补出的帧抖动 |
| A2 | 补帧的输入/中间纹理跟着 cfmt（不是写死 BGRA8） | ✓ | 16F 画布下输入仍是 8 位 ⇒ 补帧看不到 >1 的高光，补出的帧把高光压平 |
| A3 | psoCopy 的像素格式跟着 cfmt（两条相邻行：先设 colorAttachments 再用它建 psoCopy） | ✓ | 拷贝管线与纹理格式不一致 ⇒ 建管线失败或写出错位 |
| A4 | fsCopy 是直通（不做颜色变换） | ✓ | 拷贝里加了解码/编码 ⇒ 16F 与 8 位两条路径各差一次变换，画面偏暗或偏亮 |
| A5 | 不给 16F 纹理建 sRGB view | ✓ | Metal 没有 RGBA16Float_sRGB；若哪天有人「顺手」建 sRGB view，sample 会多解码一次 |
| A6 | present 管线的格式实参是变量而不是字面量 | ✓ | 写死 BGRA8 ⇒ 16F 画布用 8 位管线，高光被钳在 1.0 |
| A7 | 直方图的 linearize 由源格式决定 | ✓ | 16F 已经线性还再解一次 sRGB ⇒ 亮度整体偏暗、白点算错 |
| A8 | MetalFX 的 16F 是「先试再退」而不是写死 | ✓ | 写死 16F ⇒ 不支持的机型直接建不出补帧器（补帧整个消失） |
| A9 | MetalFX 建失败要抓异常并回退到 8 位 | ✓ | 不抓 ⇒ 抛到调用方崩掉；抓了不置 nil ⇒ 后面拿着半成品用 |
| A10 | FI 的缓存键含层格式（格式变了必须重建） | ✓ | 降级/升级 16F 后仍用旧 FI 对象 ⇒ 输入格式与 cfmt 不一致，补帧写出错 |
| A11 | cfmt 由实际建成的 MetalFX 决定，不是猜的 | ✓ | 按 want 记 cfmt 而 MetalFX 实际退回 8 位 ⇒ 纹理格式与描述符不一致 |

## 这些断言证明什么、不证明什么

证明：**代码结构**没被悄悄改回去（有人把 `f->cfmt` 改回 `MTLPixelFormatBGRA8Unorm`，这里立刻红）。

不证明：Metal 上跑起来是对的。本机没有 macOS、没有 `xcrun metal`，连 `clang -fsyntax-only`
都缺 Metal 头（见 `docs/DEVICE-ONLY.md`）。语义层面的保护是逐行 C 对账（`t_hdr_shader_mirror`、
`t_hdr_gpu_l1`、`tools/fi_domain`），运行期保护只有真机三格矩阵。

## 已经踩到的两条（都是这张表里的）

- **A2 的后果已经发生过**：`hdr_hist_add` 曾经对 16F 再解一次 sRGB（`linearize` 写死 1），
  亮度整体偏暗；现在是 A7 那条断言守着。
- **A4 的相邻问题已经发生过**：补帧的 luma 在 16F 下换成了线性域，而阈值是按 8 位编码域
  标定的（`spread` 的 `abs<0.004` ≈ 1 个码值）⇒ 静止判定命中率 100% → 44–64%，界面出鬼影。
  修法与实测见 `docs/FI-DOMAIN.md`。这条教训是写这张表的直接动机。
