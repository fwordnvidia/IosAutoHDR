# 设计：自动 SDR→HDR（L0 + L1）

## 0 一句话

在出图这一层把 SDR 画面转成 HDR：**逐帧**从亮度直方图决定扩张拐点，再用一条保色相的增益曲线把高光抬进 HDR 容器。全在 GPU 上，不回读画面；CPU 侧只有 256 个 bin 的统计。

## 0.5 输出侧的事实（决定测试怎么写）

16F 画布是 `MTLPixelFormatRGBA16Float`，**不是 sRGB 格式**：采样不解码、写入不编码。所以上屏着色器写出去的就是线性值，可以大于 1.0；端到端测试按这个模型做（若按「编码后再解回」写，>1.0 会被 `to_linear` 的 1.0 钳位吃掉，测出来的是假象）。

## 1 数据流

```
游戏出图 (BGRA8)
   │
   ├─ 每 8 帧一次：hdr_hist（compute）
   │     clear → 4×4 采样 → 256 格 log2 直方图 → knee（GPU 内）
   │     └─ 回读 4 个 float：lo, hi-lo, head, 0
   │
   └─ present fragment（每帧）
         sRGB → 线性
         y = Rec.709 亮度
         gain = 1 + (head-1)·smoothstep(lo, hi, y)
         rgb' = rgb·gain
         线性 → sRGB 编码 → 16F 画布（EDR）
```

直方图在 log2 空间分 256 格，范围 `[-10, 4]`（0.001 ~ 16 线性），覆盖 SDR 黑到 16 倍白。

## 2 L0（已有）：分位 → 拐点

```
target_hi = hist_edge(99.5 分位) / 0.8
knee_hi   = prev + (target_hi - prev)·0.1      # 死区 2%
knee_lo   = 0.55·knee_hi
```

问题：**太阳/爆炸**这类极少数超亮像素也能占到 0.5%，把 99.5 分位顶到白，于是整幅画面按「已经很亮」处理，暗景几乎没有扩张；反过来，大片 UI 白也不该被当成「高光」。

## 3 L1（本补丁）：白点 + 黑场 + 场景

### 3.1 漫反射白点

```
white = 最高一格，满足 count ≥ 0.5%·总像素（且不在黑场截断之下）
target_hi = white / 0.8
```

「白」是**面积**概念：UI、字幕、雪地、天空都是大块高值；单像素高光不是白。
0.5% 的取法来自 libplacebo 的 `black_cutoff`/`peak_percentile` 那套「按面积而非按极值」的思路（见 SOURCES §3），并做过反例测试：10000 灰 + 8 个 8.0 的太阳场景，白点仍停在 18% 灰区（t_hdr_auto_l1 用例 3）。

### 3.2 黑场截断

`log2(y) < -6`（y < 0.0156）的格子不计入统计。作用是黑边、纯黑背景不把分位往下拉，也不参与白点判定。

### 3.3 场景感知平滑

```
avg = Σ(bin_center · count) / Σcount          # log2 加权重心
d   = |avg - prev_avg|                         # 单位：stops
w   = smoothstep(0.5, 1.6, d)                  # 0 = 静止，1 = 硬切
coef = 0.1 + 0.9·w
knee_hi = prev + (target - prev)·coef
```

- `d < 0.5 stops`：完全按 L0 平滑，杜绝闪烁；
- `d > 1.6 stops`：直接跳到目标，硬切镜头不再「慢慢变亮」；
- 中间：线性过渡，避免阈值处跳变。

死区（2%）只在 `w = 0` 时生效——硬切时即便差值很小也照走，否则切场景后第一帧会被死区卡住。

## 4 数值边界

| 情形 | 行为 |
|---|---|
| 直方图全空 | 返回 0，调用方保持上一帧 |
| 全黑画面（只有 bin0） | 可算，knee 被钳到 `KNEE_L1_MIN=0.01` |
| 满屏白（白点=1.0） | knee=1.25，纯白只吃 57.5% 扩张，不再整体过曝 |
| 暗场景（白点≈0.03） | knee≈0.035，中间调才开始扩张（L0 的 0.25 下界在这里会让扩张完全失效） |
| 白点测不出（全在黑场以下） | 退回 L0 的分位算法 |
| NaN / 负亮度 | `!(y>0)` 一律进 bin0；knee 钳位兜 NaN |

## 5 复杂度与开销

| 项 | 值 |
|---|---|
| 直方图 kernel | 4×4 采样 ⇒ 每 8 帧一次，1080p 约 0.1–0.3 ms（摊 0.02–0.04 ms/帧） |
| CPU 侧 L1 | 256 次整数累加 + 几次浮点，单帧 < 5 µs，且只在使用回读时才跑 |
| 内存 | 256×4 B 直方图 + 16 B 参数缓冲 |

## 6.5 GPU 侧：L1 已经能用一条 kernel 算完

`hdr_hist.metal` 新增 `hdr_hist_l1`：一次 dispatch 出 `float4(hi, white, avg, scene)`
- `avg` 用格中心加权（不是上沿，重心要期望）
- `white` 从亮往暗扫，取「计数 ≥0.5% 且不在黑场以下」那一格的**上沿**
- 上界 `[0.01, 2.0]`（L1 自己的界，不是 L0 的 `[0.25, 1.0]`）
- 找不到漫反射白时退回 99.5 分位 + L0 的界

这样只回读 16 字节，不需要把 256 格直方图搬回 CPU。

## 6.7 与 0.4.0 自带补帧共存

- `nvn_present_fi.inc`：`NvPresentFI.cfmt` 跟着层走（16F → `MTLPixelFormatRGBA16Float`）。MetalFX 帧插值对 16F 的支持按机型/系统不同，`@try` 建不出来就退回 BGRA8 并黄字告警——补帧继续工作，只是补出的帧少 4 位。
- `fi_commit` 原先写死 `present_pipeline(MTLPixelFormatBGRA8Unorm)`，HDR 下会把 8 位管线画进 16F 画布（管线/画布不匹配）。改成按 `dr.texture.pixelFormat` 建。
- `present_blit_m4` 的 knee 只在 `uvBuffer.length >= 12*sizeof(float)` 时写：AA / MetalFX 自己的 `cropUV` 仍是 8 float，不能越界；上屏与补帧的缓冲都扩到 12。
- 16F 画布下本轮**不叠加** AA / MetalFX 空间放大（它们的内部图与上屏管线都是 8 位），打一次黄字；16F 版是下一步。

## 6.8 色域 / 饱和度（本轮新增）

线性化之后、ITM 之前插两级**默认关闭**的调色，对应 RTX HDR 面板上的饱和度与宽色域输出：

```
sRGB 采样 → s2a_lin() → [P3 混入 mix] → [保亮度饱和度 s] → ITM gain → 写 16F（线性，可 >1）
```

- `S2A_HDR_P3`（0..1，缺省 0）：sRGB → Display P3 的 BT.2087 矩阵，按 mix 线性插值。
  这是**同色异原色**的换算，不含「更艳」——所以 `t_hdr_color` 只判色相角（cos ≥ 0.995，实测最差 0.99858），
  不判色度单调（P3 空间里同一颜色的 L∞ 色度本来可大可小）。
- `S2A_HDR_SAT`（0.5..2，缺省 1）：`c' = y + (c - y) * s`，y 是 Rec.709 亮度 ⇒ 亮度不变、灰逐位不变。
  只夹负侧（`max(0, …)`），>1 的正分量必须保留 —— HDR 的高光就在那里。
- 两级都带恒等短路（`sat == 1.0f` 直接拷贝、`sat==1 && p3<=0` 直接走 `itm_rgb`），
  所以缺省包的上屏结果与没有这两个旋钮时**逐位相同**（`t_hdr_color` 第 10 组断言）。
- 上屏缓冲随之从 12 float 扩到 16（`HdrCrop = rect + edge + knee + extra`），
  写入门槛 `uvBuffer.length >= 16 * sizeof(float)`；AA / MetalFX 自己的 `cropUV` 仍是 8 float，不受影响。

## 6.9 L1b：把「纸白不动」做成硬约束（本轮新增，参考实现）

量化跑出来一个真问题：L1 的拐点由 `knee = white / 0.8`、`knee_lo = 0.55 * knee` 给出，
于是 **0.69 倍白点就开始吃增益** —— 满屏 UI 白被整体抬到 ×1.57 纸白（`t_hdr_quality` 的 UI 白那一行）。
RTX HDR 那类实现的语义是「纸白保持，白点之上才扩张」，两者不是一回事。

L1b 的规则（`s2a_hdr_auto_l1b_step`）：

| 情形 | knee_lo | knee_hi | 效果 |
|---|---|---|---|
| 常规画面 | 白点（纸白） | 1.0（SDR 裁切） | 纸白 ×1.00 不动，纯白 ×head |
| 黑底画面（截断之上像素 < 5%） | 0.02 | 1.0 | 白点估计不可信（星星就是唯一亮点），从近黑开始抬 |

实测对照（同一组合成帧，head=2）：

| 场景 | L1 纸白增益 | L1b 纸白增益 | L1 星点/高光 | L1b 星点/高光 |
|---|---|---|---|---|
| UI 白 | ×1.57 | **×1.00** | 纯白 ×1.56 | **纯白 ×2.00** |
| 暗场（星空） | — | — | 星点 ×1.50 | **星点 ×1.77** |

两端都平滑（`knee_lo` 也进状态，且不越过目标），硬切仍是 1 帧内进入 ±5%。

**尚未接进生产路径**：GPU kernel `hdr_hist_l1` 现在只回读 `float4(hi, white, avg, scene)`，
L1b 还需要「截断之上的像素占比」才能判黑底画面。要接就得改 kernel 输出并重跑 MSL 编译闸门——
当前 GitHub 账号被停用、CI 无法触发，所以这一步先留成参考实现（有单测、有数字），
等 CI 恢复再把 kernel 输出扩到 `float4 + float4(lit_frac, 0, 0, 0)`。

## 6.10 时间稳定性：噪声不会让画面「呼吸」（实测）

`t_hdr_stability.c`：同一张城市夜景，60 帧、每帧重新生成 ±N 的逐像素噪声，看白点估计与 knee 的跨帧变化。

| 噪声 | L1 knee 均值 | knee 逐帧最大变化 | 白点区间 | L1b knee_lo 区间 | L1b knee_hi 变化 |
|---|---|---|---|---|---|
| 1% | 0.452 | 0.00% | 0.3613..0.3613 | 0.0200..0.0200 | 0.00% |
| 5% | 0.487 | 0.00% | 0.3898..0.3898 | 0.0200..0.0200 | 0.00% |
| 10% | 0.544 | 0.00% | 0.4204..0.4367 | 0.0200..0.0200 | 0.00% |
| 20% | 0.655 | 0.00% | 0.5082..0.5278 | 0.0200..0.0200 | 0.00% |

两条结论：

1. **不会抽搐**。量化（1/16 stop 的 log2 格子）+ `S2A_HDR_SMOOTH` 的组合把逐帧跳变压到 0.00%，
   连 20% 的合成噪声都压得住 —— 不需要额外加迟滞/死区。
2. **噪声会让扩张变弱**。白点估计随噪声单调上移（0.3613 → 0.5082，约 +0.55 stop @20%），
   也就是「噪声越大越保守」。现实内容的噪声在 ≤5%（视频压缩大致在这个量级），此时上移约 +0.1 stop，
   可以接受；如果是模拟信号源那种 10~20% 的噪声，就要靠 `S2A_HDR_WHITE_FRAC` 调高阈值来压。

> 这一节是「量出来的」不是「推出来的」：先写好表格再看数，两个结论都是跑完之后才知道的。

## 6.11 参考 CLI：把算法从宿主里拆出来

`tools/hdr_ref.c`（约 200 行 C）复用与补丁**同一份**参数层头文件（`nvn_hdr.h` / `nvn_hdr_auto_l1.h`），
做三件事：合成/读入 8 位 PPM → 逐帧建直方图 → 出拐点与增益。作用有三个：

1. **可复现**：任何人 `cc` 一下就能拿到同一组数字，不需要 iOS SDK、不需要 Metal、不需要 CI。
2. **可回归**：`tools/ref_check.sh` 断言的 11 条全是**行为**（纸白不动、纯白到 head、黑底分支生效、
   探针不越界、两次运行逐字节一致），没有一条是像素快照 —— 这正是不依赖平台的关键。
3. **可对照**：`--algo l1` 与 `--algo l1b` 同帧跑，能直接看出「L1 把纸白抬了 29%」这件事，
   比读文档直观。

真要判画质还是得在设备上（也就是那三格矩阵）。

## 6.12 带阶：8 位台阶被放大多少（并顺手修掉一个 API 陷阱）

8 位 SDR 输入 → 16F 线性输出，中间的增益曲线一定会把相邻码值的台阶放大。`t_hdr_banding.c` 量的是
「输出台阶 / 输入台阶」这个比值（就是增益曲线的局部斜率）：

| 码值 | 输入 lin | 输出 lin | 台阶 | 放大 |
|---|---|---|---|---|
| 8 | 0.0021 | 0.0021 | 3.0e-4 | 1.000 |
| 32 | 0.0137 | 0.0137 | 7.4e-4 | 1.000 |
| 96 | 0.1144 | 0.1144 | 2.5e-3 | 1.000 |
| 160 | 0.3467 | 0.3467 | 4.8e-3 | 1.001 |
| 200 | 0.5711 | 0.7244 | 6.5e-3 | 2.473 |
| 254 | 0.9823 | 1.9623 | 8.9e-3 | 2.181 |

最坏放大 **3.35×**（码值 231），发生在 knee 区间的上沿；`knee_lo` 以下恒为 1.000（中间调连一个码都不多动）。

白点越低（knee 区间越宽）曲线越缓，这正好和「什么内容怕带阶」对上：

| 白点 | knee 区间 | 最坏放大 |
|---|---|---|
| 0.74（满屏 UI 白） | 0.74..1.00 | 6.62 |
| 0.55 | 0.55..1.00 | 4.28 |
| 0.35（典型游戏画面） | 0.35..1.00 | 3.35 |
| 0.20 | 0.20..1.00 | 2.98 |
| 0.12（夜景/太空） | 0.12..1.00 | 2.85 |

结论：**平滑渐变（天空、雾）在 3~7 倍放大会出圈**，而这类内容的白点通常低（曲线也缓），所以最坏情况
落在「高白点 + 需要平滑渐变」这个不太重叠的组合上。真要兜底就是上屏前加 ±0.5 LSB 的有序抖动，
但那要改 MSL —— 记在这里，等 CI 恢复再动。

16F 余量足够：暗部最小**相对**台阶 4.7e-2，16F 相对步长 4.9e-4 ⇒ 有 ~96× 余量，**不需要抖动来掩盖输出量化**。

### 6.12.1 顺带修掉的 API 陷阱

`nvn_hdr.h` 里曾有两个「看起来一样」的入口：`s2a_hdr_itm_rgb` 第二参数其实是 **sRGB 编码值**（内部再解码），
而 `s2a_hdr_grade_rgb` 收的是**线性光**。写带阶测试时把线性值喂给前者，输出小了两个数量级，
一开始还以为是曲线有问题。现在拆成：

- `s2a_hdr_itm_rgb(p, in_encoded[3], out[3])` —— sRGB 编码入口（保留，MSL 对照用）
- `s2a_hdr_itm_rgb_lin(p, lin[3], out[3])` —— 线性入口（新）

并加断言：256 个码值下两条入口的结果差 ≤1e-6。

## 6.13 鲁棒性：垃圾输入不许把 NaN 带进 knee

真机上拿到坏输入并不稀奇：解码失败的黑帧、DMA 里的垃圾像素、驱动给出的 `inf`、以及「上一帧状态还没初始化
就当历史用」。一条 NaN 进了 `knee` 就会污染整帧上屏，而且症状是「整屏发灰/发黑」，很难从上屏结果反推原因。

`t_hdr_robust.c`（15 项，含 20 万次 fuzz）第一版直接抓到三个洞：

| 洞 | 触发方式 | 后果 | 修法 |
|---|---|---|---|
| `s2a_hdr_to_linear(NaN)` → NaN | 像素值是 NaN | 亮度 NaN → `hist_bin` 的 `(int)inf`/NaN 转换是 UB | 判断改成 `!(c > 0)`，NaN 走 0 |
| `prev_hi`/`prev_avg` 是 NaN/Inf | 首帧状态未清、或调用方传错 | 平滑结果直接 NaN | 入口判 `isfinite`，不成立就当作没有历史 |
| L1b 的 `prev_lo > prev_hi` | 状态被外部写乱 | 插值穿过目标、区间反转 | 同上，附带 `prev_lo <= prev_hi` 校验 |

另外确认了三件**本来就对**的事：`hist_bin` 对 ±inf/±1e30/denormal 全部夹在 `[0, BINS)`；
计数全填 `0xffffffff` 时 `s2a_hdr_hist_avg` 用 `uint64` 求和 + `double` 累加不溢出；纯黑帧返回 0 让调用方保持上一帧。

> 顺带纠一个自己的判据错误：`s2a_hdr_to_srgb` 在输入 >1 时输出本来就 >1（显示参考白之上的高光，
> 由调用方按 `head` 归一），第一版断言「0..8 上必须 ≤1」是错的；正确判据是「0..1 上不越界 + 全程单调」。

## 6.15 把「带」数出来：平台阶 + 抖动的真实效果

§6.12 量的「台阶放大 3.35×」是**斜率**，不是肉眼能看见的东西。这一节改成数带：
`tools/measure_banding.py` 读 `hdr_ref --columns` 的未量化线性值，判「相邻列台阶 > 1.5% 且下方亮度 > 0.5 nit」，
并把「相邻列输出完全相同」记作**平台阶**（平台阶就是人眼看到的色带）。

测两张图（256 列横向渐变）：`sky` = 0.55..0.85 的窄带（模拟天空），`grad` = 全灰阶。
判据来源：BT.1886 暗部以下不可见 + Weber 1.5%。

| 图 | 输入不同亮度 | 输出不同亮度 | 平台阶 | 最大台阶 | 可见带 |
|---|---|---|---|---|---|
| sky（无抖动） | 78 | 78 | **178** | 1.57%（1.60 nit） | 7 |
| sky（±0.5 LSB 抖动） | 256 | 256 | **0** | 1.65%（1.55 nit） | 8 |

两条结论：

1. **抖动不减小台阶**（1.57% → 1.65%，反而略大）——它把「一条一条的带」换成「颗粒」。这是所有抖动的本质，
   指望它提高局部对比度是误解。
2. **抖动把平台阶清零**（178 → 0）。平台阶才是带感的来源：相邻两列亮度完全一样，眼睛看到的就是一条平带。

实现上，抖动就是解码前给编码值加 ±0.5 LSB 的确定性哈希噪声（与像素坐标绑定，不逐帧闪）。
**默认关闭**，因为它是「以噪换带」，要不要开取决于内容；上屏侧（MSL）等 CI 恢复再接。

## 6.16 16 位输出：把「量化损失」和「曲线带的带」分开

上一节的 178 平台阶里，有多少是**我们的曲线造成的**，有多少是**输入本来就重复**？用 `--out16`（16 位 PPM）
把上屏值按 65535 输出后就能拆开：

| sky 第 32 行 | 输入不同码 | 输出不同级 | 平台阶 | 最大台阶 | 可见带 |
|---|---|---|---|---|---|
| 8 位预览 | 78 | **59** | 197 | 2.10%（0.97 nit） | 46 |
| 16 位输出 | 78 | **78** | 178 | 1.57%（0.80 nit） | 8 |

结论（一条纠正 + 一条确认）：

1. **纠正**：178 个平台阶不是曲线的锅——输入本身只有 78 个不同码、256 列里必然有 178 次重复。
   16 位输出的级数**恰好等于输入码数 78**，一级不丢。
2. **确认**：真正被量化吃掉的是 8 位预览（78 → 59 级，可见带 46），而那是**预览文件**的损失，
   上屏走的是 `RGBA16Float`，不受影响。所以「上屏不需要抖动」这个结论成立（§6.12 的 96× 余量）。

`ref_check` 场景九把这条钉住：16 位级数必须等于输入码数，8 位预览必须更少，可见带 16 位 ≤ 8 位。

## 6.17 时间维度：淡入 64 帧不抽动

前面的测试都是「单帧快照」或「同帧重复 60 次」。真正的抽动（pumping）发生在 **APL 连续变化**时——
所以加一个 `fade` 合成序列（整帧亮度 0.18 → 1.0 逐帧爬升，顶部一条均匀带），`--seq` 逐帧导出参数与探针增益。

| 指标 | 实测 |
|---|---|
| `gain@0.5` 轨迹 | 1.0963 → 1.0000 |
| 最大单帧相对跳变 | **0.443%** |
| 增益方向翻转 | **0 次**（单调） |
| `knee_lo` 每帧最大变化 | 0.025（= 目标差的 ~10%，符合 `coef=0.1`） |
| `knee_hi` 越界 | 最大 1.000000，不越过 SDR 截断 |

含义：淡入淡出这种最考验平滑的场景下，扩张量**单调衰减到 1**，没有来回摆。`coef = 0.1 + 0.9·w`
在场景权重低时正好给出 ~10%/帧的逼近速度——既跟得上，又不会一顿一顿。

顺带一个观察：`gain@1.0`（纯白）**恒为 head=2.00**，与 APL 无关——这是 ITM 的定义（SDR 截断点映射到峰值），
不是 bug。判断扩张强弱要看中间调探针（0.5）和 knee，不能看纯白。

## 6.18 HUD 会掐死整帧：孤立簇剔除

游戏画面里最常见、也最容易被算法吃掉的情况：**静态 HUD 白字**。它只占 ~1% 的像素，却坐在 0.8 以上的高位。

复现（`--synth hud`，1080p 语义，内容白点 0.50，底部 HUD 带亮度 0.86，顶部/底部各 1/12 黑边）：

| | 白点 | `knee_lo` | 探针 0.832 增益 |
|---|---|---|---|
| 不开剔除 | **0.7424** | 0.7424 | **1.0000**（完全不扩张） |
| 开剔除 | **0.2381** | 0.2381 | **1.5793** |
| 无 HUD 的对照图 | 0.2125 | 0.2125 | 1.6008 |

也就是说：**1.2% 的 HUD 像素，把 98.8% 的画面的扩张彻底关掉了**。这不是精度问题，是设计缺陷。

修法（`s2a_hdr_sdr_white_bulk`）：从高往低扫**连续非空 bin 的簇**；最高那一簇若质量 < 亮像素的 5%
且与下方主簇之间隔着 ≥3 个空 bin（≈0.35 stop），判为 HUD/孤立高光丢掉，用下方主簇顶边当白点。
真实高亮（天空、白墙、爆炸）与主簇相连，不会被误丢——回归测试钉住：`uiwhite / city / dark / ramp`
四个场景的白点在开关两种情况下**逐位相同**。

为什么要「单 bin」才能复现：HUD 是纯色带，真机直方图里落在同一格；如果把 600 个像素摊到 3 格，
每格都不到 0.5% 分位，旧算法本来就不会被顶上去——第一版单测就是这么写错的，改成单 bin 才测出缺陷。

常数：`S2A_HDR_CLUSTER_MAX_FRAC 0.05`、`S2A_HDR_CLUSTER_GAP 3`。**默认未接上屏路径**（同样等 CI），
参考实现里用 `--hudguard` 开关，`t_hdr_hud`（16 项）+ `ref_check` 场景十一守住。

## 6.19 那两个常数为什么是 5% / 3 bin：敏感度扫描

上一节的 `S2A_HDR_CLUSTER_MAX_FRAC 0.05` 和 `S2A_HDR_CLUSTER_GAP 3` 如果只是拍的，就会有人问「为什么不是 2% 或 10%」。
`tools/sweep_hud.c` 用合成直方图把参数平面扫一遍：4 类内容 × 3 档 HUD 覆盖率（0.5%/1%/2%）必须被剔（12 例），
8 档「真实连续高亮」一个都不许误丢（8 例）。

| max_frac | gap 2 | gap 3 | gap 4 | gap 5 | gap 6 |
|---|---|---|---|---|---|
| 0.01 | 4/12 | 4/12 | 4/12 | 4/12 | 3/12 |
| 0.02 | 8/12 | 8/12 | 8/12 | 8/12 | 6/12 |
| **0.03** | 12/12 | 12/12 | 12/12 | 12/12 | 9/12 |
| **0.05 ← 默认** | **12/12** | **12/12** | **12/12** | **12/12** | 9/12 |
| 0.08 | 12/12 | 12/12 | 12/12 | 12/12 | 9/12 |
| 0.12 | 12/12 | 12/12 | 12/12 | 12/12 | 9/12 |

（所有格子的误丢都是 0/8。）

读法：

1. `max_frac` 低于 3% 时开始漏剔（HUD 覆盖率 2% 就漏），所以 3% 是下界；上界由「真实高亮最多占多少」决定，
   扫描到 20% 仍 0 误丢（因为真实高亮与主簇相连，压根不看比例）。
2. `gap ≥ 6` 开始退化——空档判据放宽后，主簇内部的小空档也会被切断，簇被拆碎、质量不足而误判。
   所以 **3 是平台中间值**，2..5 结果完全一致。
3. 默认值坐在 **16 个相邻组合全部 12/12 & 0/8** 的平台正中，不是单点。

`ref_check` 场景十二把这条钉死：默认行必须 12/12 与 0/8，且平台区至少 12 组。


### 6.16 帧率归一化（30/60/120 Hz 同一时间常数）

`S2A_HDR_SMOOTH` 是「60 Hz 下每帧走多少」。S2Arm 有 30/60/120 三档帧率，
如果直接用同一个每帧系数，120 Hz 的收敛会比 30 Hz 快 4 倍——切换档位时画面表现会变，
看起来像掉帧或抽动。

换算：`coef_hz = 1 - (1 - coef60)^(60/hz)`，即把「每帧保留比例」按时间折算。
实现 `s2a_hdr_coef_at_hz(coef60, hz)`；`hz <= 0`、NaN 按 60 Hz，`hz` 夹在 1..240。

实测（`t_hdr_framerate`，15 项）：从 0.80 收敛到目标 0.1116，

| 帧率 | 达到 95% 的帧数 | 对应秒数 |
|---|---|---|
| 30 Hz | 15 | 0.500 s |
| 60 Hz | 29 | 0.483 s |
| 120 Hz | 57 | 0.475 s |

帧数比 60/30 = 1.933、120/60 = 1.966（离散化误差内为 2）。1.0 s 后三档的 `knee_lo`
都是 0.112801（残差 0.9^60 = 1.8e-3 量级），即**同样的物理时间得到同样的画面状态**。

旧调用点（不传 `hz`）走 `S2A_HDR_SMOOTH_HZ = 60` 包装，与改造前逐位相同（测试用 `memcmp` 断言）。

**未接线**：GPU 侧的 `nvn_hdr_hist.inc` 里调用点还没传实际帧率（需要 MSL/ObjC 编译验证，
当前 GitHub 账号停用做不到）。常数与函数已就位，接线只是把 `hz` 传下去。

### 6.17 切镜阈值的取值依据（SCENE_LOW=0.5 / SCENE_HIGH=1.6）

`S2A_HDR_SCENE_LOW/HIGH` 决定「两帧 log2 重心的差多大时，判定为切镜、放弃平滑」。
这两个数以前是凭经验给的，现在有扫描数据（`tools/sweep_scene.c`）：

**单帧阶跃 → 场景权重与收敛帧数**（默认 0.5 / 1.6）

| 阶跃 (stop) | sw | 到 95% 用几帧 |
|---|---|---|
| 0.30 | 0.000 | 29 |
| 0.60 | 0.023 | 24 |
| 0.90 | 0.301 | 7 |
| 1.20 | 0.699 | 3 |
| 1.50 | 0.977 | 1 |
| ≥1.80 | 1.000 | 1 |

**匀速爬升时的稳态落后**（stop，越大越「跟不上」）

| 爬升 (stop/帧) | 默认 0.5 | low=0.25 | low=1.0 |
|---|---|---|---|
| 0.02 | 0.169 | 0.169 | 0.169 |
| 0.05 | 0.385 | 0.385 | 0.385 |
| 0.10 | 0.662 | 0.662 | 0.662 |
| 0.20 | 1.004 | 1.004 | 1.004 |
| 0.30 | 1.241 | 1.218 | 1.241 |
| 0.50 | 1.512 | 1.097 | 1.512 |
| 1.00 | 0.594 | 0.376 | 1.964 |

读法（这也是取值的理由）：

- 0.2 stop/帧 以下，`low` 取 0.25 还是 0.5 **完全一样**——把阈值调低在现实内容上买不到任何跟踪收益。
- 0.5 stop/帧 以上才出现差别，而那个速率在任何内容里都已经接近「闪光/切镜」，此时「快跟」的代价是容易被判成切镜（画面跳），所以不往下压。
- 抬到 1.0 会让 1.0 stop/帧 的落后从 0.594 恶化到 **1.964 stop**（三倍），因为权重升不上去，只能靠 0.1 的常规系数追。
- 0.8–1.0 stop/帧 处默认值的落后反而下降（0.594 < 1.512），是 smoothstep 开始给权重导致的——不是抄底，是过渡区。

结论：0.5 / 1.6 落在「现实内容无差别、极端速率仍能响应」的中间，`ref_check` 场景十三把四条关键点固化成断言。

### 6.18 CPU / GPU 两套实现必须同口径（抓到 3.5 stop 的分叉）

GPU 的 `hdr_hist_l1` 与 CPU 的 `nvn_hdr_auto_l1.h` 是两份独立实现，本机只能测 CPU 那份。
`src/t_hdr_gpu_mirror.c` 把 MSL kernel 逐行翻成 C，用同一份直方图比 `hi/white/avg/scene` 四个输出。

第一次跑就抓到：**同一份带黑边的直方图，GPU 的重心 -1.2049、CPU 的 -4.7120，差 3.5 stop。**
原因是 CPU 的 `s2a_hdr_hist_avg` 把黑场以下（含纯黑）全算进重心，MSL 那份跳过了黑场。
后果不只是数字不同：带黑边的画面重心被拽到直方图底端，不同内容都落在 ≈-4.7 附近，
**切镜检测基本失效**，暗场分支也会误判。

修法不是把 CPU 改成跳过 -6（那样星空整片被丢，重心永远算不出来），而是**两边都改成只排真黑**：
新增 `S2A_HDR_AVG_CUT = -9.5`（线性 0.0014），MSL 加 `kAvgCut = -9.5f` 并在累加循环里用它；
白点仍用 `BLACK_CUT = -6`（那里要的是「漫反射白」，排掉暗部是对的）。

| 场景 | 修前 CPU | 修后 CPU | GPU |
|---|---|---|---|
| 普通内容 | -1.2211 | -1.2211 | -1.2211 |
| 带 40% 黑边 | **-4.7120** | -1.2049 | -1.2049 |
| 纯黑 + 暗星(0.003) | 可算 | 可算（门限之上） | 可算 |
| 全黑 | 可算 | **不可测 → 保持上一帧** | 同 |

`t_hdr_gpu_mirror` 14 项锁住这四条 + 200 组随机直方图，另加 3 项「上屏 MSL 的 Lab 饱和度 vs CPU」逐通道对照；`t_hdr_auto_l1` 从 92 项加到 93 项
（全黑改为「不可测」，另加一条「纯黑+暗星仍可算」守住门限别定得太高）。

**局限**：镜像测试证明的是「按 MSL 源码逐行翻译的 C」与 CPU 一致，不能代替 Metal 真编译。
真编译仍然卡在 GitHub 账号停用。

### 6.19 切镜判据：重心 + 白点两路取大

原来只比重心 `|Δavg|`（单位 stop，阈值 0.5 / 1.6）。问题不在阈值，在**证据不够**：
菜单 → 游戏、同亮度过场、UI 层级整体重排，这些切换的整帧重心几乎不动（都是同一批中间调，
差 0.05 stop 量级），但白点会跳 0.5~1.5 stop。只看重心 ⇒ 判不出切镜 ⇒ knee 沿 10% 的斜率
爬过去，`--synth cut` 里要 **26 帧**才走完 85%。

现在两路证据取大（`s2a_hdr_scene_weight_white` + `s2a_hdr_scene_fuse`，`nvn_hdr_auto_l1.h`）：
- 白点差按 log2 比值算，**复用同一组 stop 阈值**，不引入新常数；
- 任一路测不出（白点 0 / NaN）就让它让路，不把 scene 拉成 1；
- 融合后同一场景 **1~2 帧**到位（QUALITY.md「同 APL 切镜」表）。

慢变不许误判：每帧 0.5% 的白点漂移（≈0.007 stop）在 120 帧里最大权重 **0.0000**，
`t_hdr_wiring` 第 13 组守着。

## 6.20 把直方图本体 blit 回 CPU（上屏判定不再靠代理）

上屏路径原本只有 `float4(hi, white, avg, scene)` 可读。用它反推「这是不是黑底画面」是
**信息量不足**的：`hist_avg`、`sdr_white`、`auto_knee` 三个量都只反映「亮的那部分」——
`hist_avg` 跳过低于 -9.5 的纯黑格，白点取的是 0.5% 分位。于是「全屏 0.2 灰」与
「99.9% 纯黑 + 0.1% 的 0.2 亮点」在 float4 里完全同形。

`tools/sweep_darkproxy.c` 在 240 格分布网格上量了这件事（CPU 判据 `lit_frac < 5%` 为真值）：

| 代理判据 | 判错格数 |
|---|---|
| 白点 < 2% 白（现行） | **120 / 240**（全是漏判） |
| 重心极低 + 白点高 | 99 / 240 |
| 白点-重心 gap > 5.5 stop | 96 / 240 |

所有漏判格都是 `base = 0.0`（纯黑背景）+ 少量亮簇。结论：代理上限就在这里，必须换数据。

**做法**：`NvHdrHist` 增加一块 `histcpu`（`MTLResourceStorageModeShared`，1 KB），
每次分析后用 blit 把 1 KB 直方图拷回来：

```objc
id<MTLBlitCommandEncoder> be = [cb blitCommandEncoder];
[be copyFromBuffer:f->hist sourceOffset:0
          toBuffer:f->histcpu destinationOffset:0 size:256 * sizeof(uint32_t)];
[be endEncoding];
```

完成回调里直接拿 `hist` 调 `s2a_hdr_auto_l1b_step_fused()` —— 与 `t_hdr_*`、`hdr_ref`
**同一份代码**。代价：每 `S2A_HDR_HIST_EVERY`（缺省 30）帧多 1 KB 传输与一次 blit，
按 60 Hz 算约 2 KB/s，可忽略；GPU 端原子加仍在 private 缓冲上，没有变慢。

顺带两件事一起落地：

1. **HUD 稳健白点**：CPU 上有直方图就能先跑 `s2a_hdr_sdr_white_bulk()`，把 1.2% 的
   HUD 白字剔掉再当纸白 —— 上屏路径此前做不到（只按 0.5% 分位）。
2. **融合判据**：`s2a_hdr_auto_l1b_step_fused()` 里同时看重心与白点两路
   （`s2a_hdr_scene_fuse`），同 APL 切镜从 26 帧压到 1–2 帧。

对账：`.inc` 保留一行日志，把 GPU 算出的 `white/avg` 与 CPU 直方图算出的值对比，
差 >0.02 / >0.05 就打一行 —— kernel 与头文件分叉时能立刻看见。

## 两条放置方式（并列保留，不是二选一）

| | knee（缺省） | bt2408（`--map bt2408`） |
|---|---|---|
| 定义 | 纸白以下不动，纸白以上按 smoothstep 抬到 head | `L_out = head * L^1.15`（BT.2408-8 §5.1） |
| 黑 | 0 → 0 | 0 → 0（幂函数结构） |
| 线性 0.18 | ×1.0000 | ×1.5696 |
| 线性 0.50 | ×1.0000（缺省拐点 0.55 之下） | ×1.8295 |
| 线性 1.00 | ×2.0000（head=2） | ×2.0300 |
| 观感 | 保住 SDR 对比，只把高光顶出去 | 整幅按幂函数抬到 203 nit 纸白，官方定义的「放进 HDR 容器」 |
| 适合 | 游戏画面（不想让 UI 与暗部整体变亮） | 影视内容（希望整体落在 HDR 参考白上） |

两条都由 `s2a_hdr_*` 的纯函数给出，命令行用 `hdr_convert --map knee|bt2408` 选择；
上屏路径目前只用 knee（`src/nvn_hdr_hist.inc` → `s2a_hdr_auto_l1b_step_fused_hz`）。

## 调色后超上界：等比缩放，而不是逐通道钳位

Display P3 混色与饱和度缩放都会把某个通道推高。实测 `sat=3.0`、`p3=0` 时，蓝通道可到
`head+2.05`（`head=2.0` ⇒ 4.05）。16F 画布并非「想写多大都行」：超过
`maximumExtendedDynamicRangeColorComponent` 的部分由系统**直接钳**（Apple
《Performing your own tone mapping》），钳位会切出色块并把色相推走——正是保色相的努力要避免的。

所以 `s2a_hdr_clip_head()` 用**等比缩放**：取三元组最大值 `m`，`m > head` 时整体乘 `head/m`，
只降亮度、通道比例不变；负分量夹 0。C 侧（`s2a_hdr_grade_rgb` 末尾）与上屏 MSL
（`src_msl_hdr` 的 `s2a_clip_head`）同一算式，`t_hdr_shader_mirror` 里 177,147 组组合
两侧逐通道一致，并单独断言「两侧都没有超 head 的通道」。

### knee 的跨线程发布：打包成 64 位，而不是两个 float

`g_hdr_knee[0]`（knee_lo）与 `[1]`（knee_hi - knee_lo）由 Metal 完成回调（后台队列，
每 `S2A_HDR_HIST_EVERY`=8 帧一次）写，渲染线程每帧读来填 present 的 fragment buffer。
两次独立 float 写之间存在撕裂窗口：读方可能拿到「新 lo + 旧 delta」——该帧的拐点既不是上一帧
的、也不是这一帧的（例如上一帧 [0.30,0.40]、这一帧 [0.90,1.20]，撕裂帧算成 [0.90,1.00]，
1.00–1.20 的高光被临时压平）。只在负载抖动时偶发，日志里看不到。

修法：`s2a_hdr_knee_pack/unpack/publish/take`（`nvn_hdr.h`）把 `(lo, delta)` 打包进一个
`unsigned long long`，写入用 `__atomic_store_n(..., __ATOMIC_RELEASE)`，读取用
`__atomic_load_n(..., __ATOMIC_ACQUIRE)`。`nvn_hdr_hist.inc` 的三处 knee 更新都先发布原子槽
再更新 CPU 记账；`present_blit` / `present_blit_m4` 通过 `s2a_hdr_knee_take()` 一次取到自洽的一组。
打包不变量：`delta < 0` 被夹成 0（上屏的 knee 不允许反向）。

`src/t_hdr_publish.c` 9 项守着：打包往返逐位一致（含 ±0/1e-6）、2 万组随机往返、
发布前后只可能读到整组、旧做法的撕裂帧确实既不属于旧也不属于新、从未发布时返回 0、
负 delta 夹 0、1000 组随机 `lo+delta >= lo`。

## 内容映射（`S2A_HDR_MAP=1`）

knee 档的定位是「不动 SDR 观感、只把高光顶出显示器件的能力」；它的必然结果是几乎没有可见变化
（`docs/FIDELITY.md`：码值有变化的像素 0.02%–0.41%）。游戏内容没有系统 UI 要保护，
所以另给一档把整幅放进 HDR 容器：

    L_out = head * L^1.15          （BT.2408-8 §5.1：SDR 100 → 203 cd/m²，OOTF gamma 1.15）

黑仍映射到 0（不是把黑抬灰），线性 1.0 正好落在 `head`。逐通道做 gamma 会改彩度，
因此与 ITM 同口径：按 Rec.709 亮度算等比倍数再乘三通道（相对文献的自觉偏离，见 SOURCES §9）。

上屏是 `src_msl_hdr` 里的 `c.extra.z > 0.5` 分支（`extra.z` 以前空着），
CPU 侧是 `s2a_hdr_grade_rgb_map(..., map=1, ...)`；`src/t_hdr_map.c` 把两边的逐通道差压到 2.4e-7。

## GPU 侧 L1（`hdr_hist_l1`）与主路径的已知差异

设备上的 knee **不是 GPU 算的**：`hdr_hist_add` 只数格子，1 KB 直方图 `copyFromBuffer` 回 CPU，
`s2a_hdr_auto_l1b_step_fused_hz` 在 CPU 上算 L1b 再 publish 给渲染线程。`hdr_hist_l1` 这个 kernel
建了管线（`ps_l1`）但**从未被调度**，只有 blit 失败时调用方才可能回退到它。

它的行为由 `src/t_hdr_gpu_l1.c` 逐行对账（把 MSL 翻成 C，用同一份直方图跑 CPU 参考实现）：

| 项 | MSL（float） | CPU 主路径（double） | 结论 |
| --- | --- | --- | --- |
| `avg` | −1.975795 | −1.975795 | 差 5.96e-07 stop（float 累加误差，可忽略） |
| `white` | 1.310961 | 1.310961 | 同格（同一条「最高一个计数 ≥ 0.5% 的格」判据） |
| `need` 量化 | `(uint)((float)total*0.005f)` | `(uint64_t)((double)total*0.005)` | 1..200000 逐个比较差 **0** 个 |
| `scene` | 0.66 stop → 0.311394 | 0.311394 | 逐位一致 |

**唯一的真差异是 HUD**：MSL 的 white 没有簇剔除（主路径用 `s2a_hdr_sdr_white_bulk`）。
同一份「内容主体 + 2.4% 孤立 HUD 白条」的直方图：MSL 白点被顶格拉到 **13.24**（hi 打满上限 2.0），
CPU bulk 给 **0.4204**（hi 0.5256）。后果不是「画面变亮」而是**扩张失效**——knee_hi=2.0 意味着
只有 2.0 以上的亮度才吃增益，8 位 SDR 内容永远够不着。

不修的理由：这条 kernel 从未被调度；剔除要求两遍扫（找 top → 判 gap → 再扫），在单线程
compute kernel 里做等于把 256 格扫三遍。真要让 GPU 算 knee 时再补，届时 `t_hdr_gpu_l1.c`
的第 8 条断言会立刻变成红的（它断的是「MSL 白点比 CPU bulk 高 1 stop 以上」这个当前事实）。
